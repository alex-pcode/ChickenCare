# Story 8.2: Service Worker Registration and Install Prompt Handling

## Status

Ready for Review

## Story

**As a** returning ChickenCare user,
**I want** the app to register its service worker on first load and update cleanly on deploys,
**so that** PWA features activate without breaking after a new release.

## Acceptance Criteria

1. A root-scoped service worker is served from `public/sw.js` rather than `/build`, so the default scope is `/` and covers all Laravel routes, HTMX navigations, and first-party static assets.
2. `resources/js/app.js` registers the service worker only when `navigator.serviceWorker` exists and the app is running in a production-capable secure context (`https:` or localhost/loopback); unsupported or insecure contexts skip registration without errors.
3. The service worker uses an explicit versioned cache namespace, for example `chickencare-sw-v<SW_VERSION>`, and removes obsolete `chickencare-sw-*` caches during `activate`.
4. This story sets the lifecycle policy to wait-for-reload, not forced takeover: the worker does not auto-apply unconditional `skipWaiting()` or `clients.claim()` on deploy, and when a new worker reaches `waiting` the UI shows a dismissible non-modal update notice with a reload action.
5. The `beforeinstallprompt` event is intercepted, stored, and exposed through a small unobtrusive install affordance rendered in the Blade shell; the browser install prompt appears only after explicit user action and never as an intrusive modal.
6. Service worker registration and install-prompt handling failures are logged to the browser console for debugging and never block HTMX, Alpine, or the initial page render.
7. Removing the registered service worker in browser DevTools returns the app to normal non-PWA behavior on the next reload, with no code changes or server-side toggle required.

## Dev Notes

### Source Findings

- `resources/js/app.js` already owns global frontend bootstrapping, including HTMX event handlers and global frontend state. Service worker registration should live in the same entrypoint rather than in page-specific scripts.
- Both `resources/views/layouts/app.blade.php` and `resources/views/layouts/guest.blade.php` load the same Vite entrypoint, so one registration path can cover both authenticated and guest sessions.
- Existing transient flash and toast patterns are not a perfect fit for update and install actions, so a small reusable notice surface is justified.

### Dependencies and Shared Contracts

- Depends on Story 8.1 so manifest wiring and install metadata already exist before install-prompt handling is added.
- Builds on Story 7.1 for static-asset cache rules and Story 7.2 for conservative handling of dynamic responses.
- Establishes the shared service-worker contract for later stories:
  - Service worker URL: `/sw.js`
  - Root scope: `/`
  - Version namespace: `chickencare-sw-v<SW_VERSION>`
  - Update policy: user-visible wait-for-reload, not forced takeover
  - Client-side PWA state survives HTMX body swaps through global state or window/document events
- Story 8.3 depends on this lifecycle, scope, and cache-versioning contract before adding offline-read caching.
- Story 8.4 depends on this registration path before adding Background Sync and queue replay.
- Story 8.5 depends on this exact `sw.js` serving path and update contract when defining Apache and Plesk deployment behavior.
- Story 8.6 depends on this story to verify service worker serving, update flow, and install affordance behavior.

### Implementation Notes

- This story establishes registration, lifecycle, and prompt handling only. Offline read caching belongs to Story 8.3, and offline write replay belongs to Story 8.4.
- Use an explicit `SW_VERSION` constant for the initial implementation rather than deriving the version from the Vite manifest. This keeps `public/sw.js` root-scoped, Apache-served, and easy to bump intentionally on release.
- Forced mid-session takeover is more likely to disrupt HTMX navigation or in-progress forms than it is to help, so the default should remain user-driven activation.

### Improvements Checklist

- [ ] **Dark mode support for PWA banner**: `_pwa-banner.scss` has no `.dark` overrides. The toast component (`_toast.scss`) — visually similar — has dark mode styling. The banner's hardcoded `background: rgba(255, 255, 255, 0.96)` and dark text colors will look wrong in dark mode.

### Security Review

No security concerns. The service worker is minimal (no fetch handler, no caching of responses). Registration is correctly gated behind secure contexts. The `SKIP_WAITING` message handler only calls `self.skipWaiting()` with no arbitrary code execution. The `PWA_PING`/`PWA_PONG` message handler returns only the version string.

### Performance Considerations

No performance concerns. Registration is deferred to `window.load`. The service worker's install handler only opens an empty cache. No fetch interception means zero runtime overhead on network requests. The banner component uses `x-cloak` to prevent FOUC.
