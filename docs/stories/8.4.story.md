# Story 8.4: Offline Write Queue with Background Sync

## Status

Ready for Review

## Story

**As a** ChickenCare user recording data near the coop with no signal,
**I want** my form submissions to be saved locally and synced automatically once I am online,
**so that** I never lose an egg count, death record, or feed entry because of bad connectivity.

## Acceptance Criteria

1. A small client module intercepts submissions from a defined allowlist of existing HTMX create forms only: egg entry create, death record create, feed inventory create, and expense create.
2. When the request fails due to offline state (`navigator.onLine === false` before submit, or a network or fetch rejection during submit), the submission payload is persisted to IndexedDB through a minimal wrapper. Stored data includes the target URL, HTTP method, CSRF token snapshot, serialized form fields, created timestamp, retry metadata, and queue item identifier.
3. The UI immediately behaves like a successful submit for the allowlisted forms: it resets the form, leaves the user on the current screen, and shows an optimistic existing-style toast message equivalent to `Saved offline — will sync`.
4. The service worker from Story 8.2 registers a Background Sync tag for queued writes when supported. Browsers without Background Sync use a lightweight page-level fallback driven by `online` and `visibilitychange` listeners that attempts replay when the app regains connectivity.
5. Replay submits the same request shape the online flow already uses against the original Laravel routes, refreshing the CSRF token first via a lightweight authenticated `/csrf-token` endpoint rather than inventing a new create API.
6. On successful replay, the queue item is removed exactly once and the user receives a subtle existing-style confirmation equivalent to `Synced`. Local replay orchestration prevents duplicate submission of the same queue item even if both Background Sync and fallback listeners fire.
7. A `419` response triggers exactly one retry after fetching a fresh CSRF token. If the retry still fails, the item is moved to a failed bucket instead of being dropped silently.
8. Non-retryable failures move the item to a failed bucket surfaced in the existing account area so the user can review and discard unresolved submissions. This includes non-retryable `4xx` responses other than `419` and unexpected interactive HTML responses that indicate the request could not be completed automatically.
9. Routes outside the allowlist remain online-only. Updates, deletes, sales, CRM, account/settings actions, auth flows, JSON endpoints, and file-upload forms continue to show a clear offline error and are not queued.
10. No existing server-side controller, form request, or policy for the allowlisted create flows is modified. The queue replays the same CSRF-protected Laravel requests the online HTMX flow already produces.

## Dev Notes

### Source Findings

- The current authenticated route structure already exposes the four candidate create endpoints needed for the allowlist and they already follow the repo's dual-response HTMX pattern.
- The app already exposes an existing toast channel and an authenticated account area, so the first offline queue UX can reuse current notification and account-shell patterns.
- HTMX lifecycle listeners need to bind above the body-swap boundary because boosted swaps replace the body element.

### Dependencies and Shared Contracts

- Depends on Story 8.2 because Background Sync, service-worker scope, and replay orchestration require the registration and lifecycle contract defined there.
- Recommended after Story 8.3 because the HTMX-safe offline notice pattern and offline-state UX will already be established, but Story 8.3 is not a hard prerequisite for implementing the queue itself.
- Establishes the shared offline-write contract:
  - Initial queue allowlist is limited to create flows for eggs, deaths, feed, and expenses
  - Replay uses the original Laravel routes and payload shapes
  - `/csrf-token` is the only new server-side seam
  - Duplicate prevention is owned by queue-item locking and replay classification
  - Failed replay items surface in the account area, not in a separate admin surface
- Story 8.6 depends on this story for queue verification evidence, whether through JS tests or a documented manual verification script.

### Implementation Notes

- A minimal IndexedDB wrapper is preferred over a large abstraction layer because the queued payloads are simple scalar form submissions.
- The service worker cannot show UI directly. Replay success and failure notifications should reach the page through `postMessage` or a shared client-side notification bridge, then dispatch existing toast events.
- Because the initial allowlist consists only of scalar, date, text, and number inputs, payload serialization can stay simple. Any future form that introduces file inputs remains online-only until designed separately.
