# Story 3.1: Flock Profile & Events

## Status

Done

## Story

**As a** premium user,
**I want** to see an overview of my flock and track flock lifecycle events,
**so that** I have a central view of my flock status and history.

## Acceptance Criteria

1. `FlockProfile` model, migration, factory, seeder, policy
2. `FlockEvent` model, migration, factory, seeder, policy

10. Events timeline in chronological ascending order (oldest first)

## Dev Notes

### Project Context

This is the first story of **Epic 3: Flock & Batch Management**, introducing premium-tier flock management. The flock profile is a singleton per user (auto-created on first visit). FlockEvents are lifecycle entries displayed on a timeline.

**Reference implementation:** `D:\Koke\Aplikacija\src\components\features\profile\Profile.tsx` and `D:\Koke\Aplikacija\src\components\features\flock\FlockOverview.tsx`

### Database Schema (from architecture)

**`flock_profiles` table:**
- `id`, `user_id` (UNIQUE, FK cascade), `farm_name` (default 'My Chicken Farm'), `location`, `flock_size`, `breed` (comma-separated), `start_date`, `hens`, `roosters`, `chicks`, `brooding`, `notes`, timestamps
- Migration already mapped: `2026_04_07_000002_create_flock_profiles_table.php`
- **Note:** `farm_name`, `location`, `breed` are legacy fields from the MVP. They remain in the DB schema for data compatibility but are NOT exposed in the UI. Do not add form fields for them.

**`flock_events` table:**
- `id`, `flock_profile_id` (FK cascade), `date`, `type` (enum: acquisition, laying_start, broody, hatching, other), `description` (max 500), `affected_birds`, `notes`, timestamps
- Index: `idx_flock_events_profile_date (flock_profile_id, date)`
- Migration already mapped: `2026_04_07_000003_create_flock_events_table.php`

### Existing Migrations

### Auto-Create Profile Pattern

Unlike the original story draft, there is no separate "create profile" form. The profile is auto-created when a premium user first visits `/app/flock`:

```php
public function index(Request $request)
{
    $profile = $request->user()->flockProfile 
        ?? $request->user()->flockProfile()->create();
    
    $events = $profile->flockEvents()->orderBy('date', 'asc')->get();
    // ...
}
```

This matches the original React app where the profile is transparently loaded/created.

### Flock Overview — Batch Stats Aggregation

The Flock Overview section shows stats computed from batch data, NOT from the profile's bird count fields. This matches the original `FlockOverview.tsx`:

```php
// In FlockProfileController@index
$batches = $request->user()->flockBatches()->active()->get();

$flockStats = [
    'laying' => $batches->filter(fn($b) => $b->actual_laying_start_date)
        ->sum(fn($b) => max(0, $b->hens_count - $b->brooding_count)),
    'not_laying' => $batches->filter(fn($b) => !$b->actual_laying_start_date && $b->hens_count > 0)
        ->sum(fn($b) => max(0, $b->hens_count - $b->brooding_count)),
    'brooding' => $batches->sum('brooding_count'),
    'roosters' => $batches->sum('roosters_count'),
    'chicks' => $batches->sum('chicks_count'),
    'laying_batches' => $batches->filter(fn($b) => $b->actual_laying_start_date && $b->hens_count > 0)->count(),
];
```

**Cross-story dependency:** The `flockBatches()` relationship and `FlockBatch` model are created in Story 3.2. Until then, this section shows the promo card. The controller should handle the case where the relationship doesn't exist yet (empty collection fallback).

### Flock Overview — Conditional Rendering

Three states following the original `Profile.tsx`:

1. **Batches exist with birds** → Show stat cards grid + "Manage Batches" button
2. **No batches exist** → Show promo card ("Batch Management Available!") with benefits list and "View Batch Manager" link
3. **Profile has bird counts but no batches** → Show migration notice nudging user to adopt batch management

The brooding stat card is only shown when at least one batch has `brooding_count > 0` (conditional column in grid).

### Event Form UX — Dedicated Section, Not Inline

The original React app has the event form as a **separate section above the timeline**, not inline within timeline items. The same form is reused for both create and edit:

- **Create mode:** Empty form, title "Add New Event", submit button "Add Event"
- **Edit mode:** Form pre-filled with event data, title "Edit Event", submit button "Update Event" + "Cancel Edit" button
- When user clicks "Edit" on a timeline event, the form section scrolls into view and switches to edit mode via HTMX

HTMX implementation:
```html
<!-- Edit button on timeline event -->
<button hx-get="{{ route('app.flock.events.edit', [$profile, $event]) }}"
        hx-target="#event-form-container"
        hx-swap="innerHTML scroll:#event-form-container:top">
    Edit
</button>
```

The form partial handles both modes via `$mode` variable ('create' or 'edit') and optional `$flockEvent`.

### Timeline Sort Order

Events are sorted **ascending** (oldest first) — matching the original React app's `new Date(a.date) - new Date(b.date)`. This is chronological reading order (story unfolds top to bottom).

### Premium Tier Enforcement

Routes go inside the existing `Route::middleware(['premium'])` group in `routes/web.php` (line 27). The `EnsurePremiumTier` middleware (aliased as `premium`) handles both HTMX and standard requests:
- HTMX requests → returns premium-gate partial (200)
- Standard requests → redirect to `/app` with flash warning

### HTMX Dual Response Pattern

Every mutating controller action must handle both paths (established in Epic 2):
```php
if ($this->isHtmx($request)) {
    return view('flock.partials.some-partial', [...]);
}
return redirect()->route('app.flock.index')->with('success', 'Message');
```
Use the `HandlesHtmx` trait (located at `app/Traits/HandlesHtmx.php`) which provides `isHtmx()`, `htmxRedirect()`, and `htmxTrigger()` methods.

### Timeline Component

Use the existing `<x-ui.timeline>` Blade component (at `resources/views/components/ui/timeline.blade.php`). Events should display with type-specific color badges and Lucide SVG icons. Each event supports edit (loads form above) and delete (fade-out).

### Coding Standards Reminders

- **Ownership scoping:** Always query from `$request->user()->flockProfile()` — never `FlockProfile::find()`
- **Validation in Form Requests only** — no `$request->validate()` in controllers
- **No raw HTML output** — use `{{ }}` only
- **Policies for authorization** — never check ownership in controllers directly
- **Models are thin** — `$fillable`, `$casts`, relationships, scopes only
- **BEM SCSS naming** — `.flock__element--modifier`

### Accessibility Requirements

- Event form: `aria-invalid="true"` + `aria-describedby` on error fields, `role="alert"` on error messages
- Timeline events: each event item should have clear labels for edit/delete buttons (`aria-label="Edit event: {description}"`)
- Stat cards: accessible text for screen readers (not relying on icons alone)
- Flash messages: `role="alert"` + `aria-live="polite"` for success, `aria-live="assertive"` for errors
- Empty state: `role="status"`

Per the architecture, flock views go in `resources/views/flock/` with partials in `resources/views/flock/partials/`. The directory may not exist yet — create it.

### Improvements Checklist

- [ ] **BUG: Variable name mismatch in `FlockProfileController::update` HTMX branch** — Line 65 passes `compact('flockProfile', ...)` but `flock-overview.blade.php:15` references `$profile`. The `isset($profile)` check will always be false, so the migration notice will never render after an HTMX profile update. **Fix:** Change to `$profile = $flockProfile;` before the view call, or rename the variable in the compact to `'profile' => $flockProfile`.
- [ ] **FlockEventPolicy::create has incorrect signature** — The `create` policy method accepts `(User $user, FlockEvent $flockEvent)` but Laravel's `create` gate is invoked *before* the model instance exists. The correct signature is `create(User $user)`. This method is currently dead code (never called via `Gate::authorize`), but is a latent bug if ever invoked. If you need to check profile ownership at the policy level, pass the `FlockProfile` as a second argument: `create(User $user, FlockProfile $flockProfile)`.
- [ ] **FlockEventController::create lacks authorization** — The `create()` method at line 16 returns the event form for any `$flockProfile` without verifying ownership. A premium user could load the create form for another user's profile by guessing the profile ID. The form request protects `store`, but the `create` action should also verify the user owns the profile (e.g., `Gate::authorize('view', $flockProfile)` or `$this->authorize('view', $flockProfile)`).
- [ ] **(Low) Duplicated batch stats computation** — The batch stats array is copy-pasted between `index()` (lines 28-37) and `update()` (lines 54-63). Consider extracting to a private method `buildFlockStats(Collection $batches): array` on the controller to reduce duplication and risk of divergence.
- [ ] **(Low) Unnecessary `method_exists` check** — The `flockBatches()` relationship already exists on User model (line 66-69). The `method_exists` guard is dead code. Can be removed for clarity.

### Security Review

- **Authorization gap on `FlockEventController::create`** — Any premium user can load the event form for any flock profile. While the actual `store` action is protected by `StoreFlockEventRequest::authorize()`, the form exposes route information (profile ID in action URL). Low practical risk but violates the "Policies for authorization" coding standard.
- **All mutating actions properly authorized** — `update` and `destroy` use `Gate::authorize`, `store` uses form request authorization.
- **Ownership scoping in `index`** — Correctly queries from `$request->user()->flockProfile`.
- **No raw HTML, no SQL injection vectors** — All user content uses `{{ }}` escaping.
