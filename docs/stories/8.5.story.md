# Story 8.5: Plesk and Apache Deployment Configuration for PWA

## Status

Ready for Done

## Story

**As a** ChickenCare operator deploying to Plesk,
**I want** the service worker, manifest, and related static PWA files to be served correctly by Apache and any Plesk proxy layer,
**so that** PWA registration, scope, updates, and offline behavior work reliably in production instead of failing silently.

## Acceptance Criteria

1. HTTPS is enforced on the production domain so the service worker never attempts to register on an insecure origin.
2. `public/.htaccess` contains rewrite exceptions placed before the Laravel front-controller rewrite so `/sw.js` and `/manifest.webmanifest` are served as static files and never rewritten to `index.php`.
3. `public/.htaccess` declares `AddType application/manifest+json .webmanifest` and `AddType application/javascript .js`.
4. `public/.htaccess` forces `sw.js` to return `Cache-Control: no-cache, no-store, must-revalidate` without changing the immutable policy for hashed `/build/assets/*` JavaScript.
5. The manifest and PWA icons follow the Story 7.1 unhashed-media cache policy rather than the immutable policy reserved for fingerprinted build assets.
6. If Plesk uses nginx in front of Apache, the effective directives are reviewed so the `sw.js` cache policy and any future `Service-Worker-Allowed` response are not stripped or overwritten; the chosen deployment mode is recorded in `DEPLOY.md`.
7. The service worker is served from the site root with default scope `/`; the non-root `Service-Worker-Allowed` escape hatch is documented in `DEPLOY.md` but not enabled by default.
8. Subdirectory deployments are out of scope, and `DEPLOY.md` states that ChickenCare must be hosted at a domain or subdomain root.
9. `DEPLOY.md` includes a post-deploy verification checklist using `curl -I` and browser DevTools checks for MIME type, cache headers, scope `/`, update pickup, and installability.

## Dev Notes

### Source Findings

- `DEPLOY.md` already identifies production as a Plesk-hosted Apache deployment with Let's Encrypt and a document root pointed at `public/`.
- `public/.htaccess` already owns static-file cache behavior and Laravel front-controller rewrites, so PWA static delivery should stay at the web-server layer rather than in Laravel middleware.
- Story 7.1 already established the shared cache contract: hashed `/build/assets/*` are immutable, while unhashed public media use short `must-revalidate` caching.
- Epic 8 requires `public/sw.js` and `public/manifest.webmanifest` to be served as first-party root files so Stories 8.1 and 8.2 can function in production.

### Dependencies and Shared Contracts

- Depends on Story 7.1 for the asset-cache split between fingerprinted build assets and unhashed public files.
- Depends on Story 8.1 for the final manifest and icon paths that must be served in production.
- Depends on Story 8.2 for the final `sw.js` path, root scope, and version-bump behavior that production deploys must preserve.
- Establishes the shared deployment contract:
  - Apache remains the owner of static PWA file delivery, MIME typing, and cache headers through `public/.htaccess`
  - `sw.js` is always a root static asset with no-cache semantics
  - Manifest and PWA icons remain unhashed public assets under the Epic 7 cache rules
  - Root hosting is a hard contract for this PWA implementation
  - If nginx fronts Apache, it must preserve the required response headers
- Story 8.6 depends on this story for production verification expectations and rollback guidance.

### Implementation Notes

- This is a deployment and operations story, not a feature UX story. The goal is correct production serving behavior for files introduced by Stories 8.1 and 8.2.
- Matching order in `public/.htaccess` matters. Static-file carve-outs for `/sw.js` and `/manifest.webmanifest` must be evaluated before the fallback rewrite to `index.php`.
- The `sw.js` cache rule must be path-specific. A broad `.js` no-cache rule would break the immutable caching strategy established in Story 7.1.

## Testing

- Primary validation is deployment-focused and must run against a production-style Plesk environment rather than only local Laravel or Vite dev servers.
- Use `curl -I` to verify `sw.js`, `manifest.webmanifest`, and representative PWA icon URLs for status, MIME type, and cache headers.
- Use Chrome DevTools to verify service worker scope `/`, activation state, manifest parsing, and installability with no insecure-origin, MIME-type, or scope warnings.
- Bump the service worker version from Story 8.2 and confirm an already-installed client picks up the new worker on the next navigation.
