# Story 2.5: Egg Entry UX Enhancements

## Status

Done

## Story

**As a** user,
**I want** a streamlined egg logging form with duplicate protection and the ability to backfill historical data,
**so that** I can enter data quickly, avoid mistakes, and get started with past records.

## Acceptance Criteria

1. **Advanced logging toggle:** Size and color fields are hidden by default behind a "Detailed tracking" checkbox; toggling off clears those fields
2. **Duplicate entry detection:** On `store`, if an entry with the same date + size + color already exists for that user, return a confirmation prompt instead of silently creating a duplicate
3. Duplicate confirmation handled via HTMX: response includes a confirmation partial with "Update existing" and "Cancel" actions
4. If user confirms update, the existing entry is updated (merged) rather than a new one created
5. **Historical backfill:** When user has no entries, a "Backfill History" button appears next to the form title
6. Backfill button opens a modal (Blade partial loaded via HTMX GET) for bulk entry of historical data
7. Backfill modal allows entering multiple date/count pairs (simple repeating row form) and submits as a batch
8. Backfill limited to 90 days in the past maximum
9. All new interactions follow existing HTMX patterns (partials, dual response)
10. Existing CRUD functionality unchanged — no regressions

## Dev Notes

### Project Context

This is the second **addendum to Epic 2** closing UX gaps from the original app (`EggCounter.tsx` in d:\Koke\Aplikacija). The original app had: advanced logging toggle, duplicate detection with confirm dialog, and a historical backfill modal.

### Technology Decision: Client-Side Toggle

The advanced logging toggle needs a client-side show/hide. Check what's available:
- **If Alpine.js is loaded:** Use `x-data` / `x-show` (preferred, matches Laravel ecosystem)
- **If not:** Use `<details><summary>` for zero-JS progressive enhancement, or a minimal inline script
- **Do NOT add a new JS framework** just for this toggle

### Duplicate Detection Logic

The original React app checks duplicates on the client before submitting. In our server-rendered approach, detection happens server-side in the controller:

```
1. User submits form
2. Controller checks: existing entry with same (user_id, date, size, color)?
3. If yes → return confirmation partial (HTMX) or redirect with warning (standard)
4. User confirms → re-submit with confirm_update=1 → controller updates existing
```

This is cleaner than client-side detection and guarantees consistency.

**Null handling:** When size or color is null, the duplicate check should match on `(date, NULL, NULL)` — use `whereNull` for null values, not `where('size', null)`.

### Backfill Scope

The original app's `HistoricalEggTrackingModal` is a premium-aware feature. In ChickenCare, egg tracking is the free tier feature, so backfill should be available to all users. Limit complexity:
- Simple date + count pairs only (no size/color in backfill — keep it fast)
- 90-day lookback maximum
- No duplicate detection during backfill (bulk operation, user takes responsibility)

### HTMX Patterns

Follow the established dual-response pattern from Story 2.2:
- HTMX requests (`HX-Request: true`) → return Blade partials
- Standard requests → redirect with flash message
- Use `hx-target`, `hx-swap`, and `hx-trigger` consistently

### Accessibility

- Duplicate confirmation: `role="alertdialog"`, `aria-labelledby`, `aria-describedby`
- Advanced toggle: checkbox with `aria-controls` pointing to the collapsible section, section has `aria-expanded`
- Backfill modal: `role="dialog"`, `aria-modal="true"`, focus trap on open, return focus on close

### Code Quality Assessment

Strong UX enhancement implementation. The three features (advanced toggle, duplicate detection, backfill) are cleanly integrated without disrupting existing CRUD functionality.

**Duplicate detection** is the most nuanced piece — the null handling is correct, using `whereNull('size')` / `whereNull('color')` instead of `where('size', null)` (which would fail silently in SQL). The `whereDate()` usage addresses SQLite/MariaDB date comparison differences. The confirm flow via `hx-vals='@json(...)'` round-trips form data through the client, but since validation re-runs on the confirm path, this is safe.

**Backfill** is appropriately scoped: simple date+count pairs only (no size/color), 90-day limit enforced server-side via `BackfillEggEntriesRequest`, entries created via `$request->user()->eggEntries()->create()` for ownership scoping. The HTMX redirect on success triggers a full page refresh — correct behavior since the user wants to see all new entries.

**Advanced toggle** uses Alpine.js `x-data`/`x-show` with `x-bind:disabled="!detailed"` which prevents disabled fields from being submitted by browsers. The `[x-cloak]` CSS addition is a useful global utility.

The **form-card component fix** (`$attributes` merged onto `<form>` instead of wrapper div) is a cross-cutting improvement that benefits all form-card usages project-wide.

### Security Review

No concerns. Duplicate detection is scoped to the authenticated user's entries. Backfill creates via relationship (`$request->user()->eggEntries()->create()`). The confirm-update flow re-validates all form data through `StoreEggEntryRequest` on the round-trip, preventing tampering. `@json()` in `hx-vals` safely serializes data. No new XSS vectors — all output uses `{{ }}`.

### Performance Considerations

Minor note: the backfill controller creates entries one at a time in a foreach loop. For the expected use case (5-20 entries), this is fine. At larger scale, a batch insert (`EggEntry::insert()`) would be more efficient, but would bypass model events and timestamps. Current approach is pragmatically correct.

The duplicate check adds 1 query per store request. The query uses the `idx_egg_entries_user_date` composite index for the date filter, and the enum columns are small — negligible cost.
