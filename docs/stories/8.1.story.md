# Story 8.1: Web App Manifest and Install Experience

## Status

Ready for Review

## Story

**As a** ChickenCare user on a mobile device,
**I want** to install ChickenCare to my home screen and launch it fullscreen,
**so that** it feels like a native app I can open with one tap.

## Acceptance Criteria

1. A `public/manifest.webmanifest` file is served as a first-party static asset and declares the install metadata for ChickenCare: `name`, `short_name`, `description`, `start_url` set to `/app`, `scope` set to `/`, `display` set to `standalone`, and `background_color` and `theme_color` sourced from documented SCSS design tokens already used by the app shell.
2. The manifest declares three install icons under `public/images/pwa/`: a `192x192` maskable icon, a `512x512` maskable icon, and a standard `512x512` icon, all reachable by stable public URLs and declared with the correct sizes, types, and `purpose` values.
3. The authenticated Blade shell in `resources/views/layouts/app.blade.php` links the manifest, emits a `theme-color` meta tag, and declares an `apple-touch-icon` path for iOS install support without disrupting the existing first-paint styles, theme-cookie bootstrap, HTMX boost behavior, or Vite asset loading.
4. The manifest and PWA icons are served as unhashed public assets, not Vite build outputs, and follow the Epic 7 cache contract: `manifest.webmanifest` uses the conservative root-public-file policy, icons under `/images/pwa/` use the unhashed `/images/*` policy, and none of these assets are served with immutable caching.
5. Chrome DevTools Application > Manifest reports no manifest parse errors and shows the expected app name, start URL `/app`, scope `/`, standalone display mode, background color, theme color, and icon set.
6. From an authenticated session in Android Chrome and iOS Safari, Add to Home Screen or Install app is available and the installed app opens the authenticated dashboard route `/app` in standalone mode without browser chrome while the session remains valid.
7. The chosen SCSS token source of truth for `theme_color` and `background_color` is documented in implementation notes so future visual theme changes update the manifest deliberately instead of drifting via copied hex values.

## Dev Notes

### Source Findings

- `resources/views/layouts/app.blade.php` is the authenticated application shell and already owns head metadata, first-paint styles, the theme-cookie bootstrap script, and the shared `@vite` bundle.
- `resources/views/layouts/guest.blade.php` is a separate guest/auth shell, so this story must avoid introducing regressions outside the authenticated app layout even if manifest wiring remains scoped to the main app shell.
- `routes/web.php` maps the authenticated dashboard route to `/app`, which makes `/app` the correct install launch target for this story.
- Epic 7 already defined the cache split between hashed build assets and unhashed public files, so the manifest and icons must stay outside the immutable asset path.

### Dependencies and Shared Contracts

- Depends on Story 7.1 being in place so the public-file cache behavior is already defined for root files and public images.
- Establishes the shared contract later stories rely on:
  - Manifest URL: `/manifest.webmanifest`
  - Install start URL: `/app`
  - PWA scope: `/`
  - Icon base path: `/images/pwa/`
  - Manifest colors come from documented SCSS tokens, not copied ad hoc values
- Story 8.2 depends on this story's manifest URL, start URL, and scope contract before adding service worker registration and install-prompt handling.
- Story 8.3 depends on these stable public manifest and icon URLs for precache and offline-read behavior.
- Story 8.5 depends on these exact public paths when hardening Apache and Plesk MIME, rewrite, and cache behavior in production.
- Story 8.6 depends on this wiring to build feature tests and Lighthouse installability verification.

### Implementation Notes

- Keep the manifest and icons in `public/` so they are first-party static assets and remain outside the immutable `/build/assets/*` contract.
- Use the authenticated dashboard shell at `/app` as the install launch target because that is the existing dashboard entry point.
- Treat iOS support in this story as metadata wiring only: `apple-touch-icon` and standalone launch verification are in scope, but service worker or install-prompt behavior is not.
- Validation should be run against a built environment or real public-file serving path, not only through the Vite dev server, because cache headers and installability depend on real static asset delivery.
