# Story 4.3: Customer CRM

## Status

Ready for Review

## Story

**As a** premium user,
**I want** to manage my egg customers with contact info and status,
**so that** I can maintain buyer relationships.

## Acceptance Criteria

1. `Customer` model with `$fillable`, `$casts`, `belongsTo(User)`, `hasMany(Sale)` relationships
2. Migration: `customers` table with all columns per data model spec (`id`, `user_id`, `name`, `phone`, `notes`, `is_active`, timestamps)
3. `CustomerFactory` with realistic fake data
4. `CustomerSeeder` that creates 5-10 customers per premium user
5. `CustomerPolicy` with view/update/delete ownership checks
6. `CustomerController` with `index`, `store`, `update`, `destroy` actions using `HandlesHtmx` trait
7. `StoreCustomerRequest` form request with validation rules
8. `customers/index.blade.php` with inline HTMX CRUD, search, and active/inactive filtering
9. `customers/partials/entry-row.blade.php` — single row partial for HTMX swap
10. `customers/partials/edit-form.blade.php` — inline edit form partial
11. `customers/partials/table.blade.php` — table body partial for HTMX search/filter swap
12. Search filters customers by name (case-insensitive `LIKE` query)
13. Active/inactive filtering via `?status=` query param (default: active only)
14. Soft deactivation (`is_active` flag toggle) instead of hard delete
15. Delete uses `hx-confirm` + fade-out animation
16. Dual response: HTMX requests get partials, standard requests get full page
17. `<x-ui.empty-state>` shown when no customers match current filter
18. Feature SCSS: `_crm.scss` with BEM naming, added to `app.scss`
19. All queries scoped to authenticated user via `$request->user()->customers()`

## Dev Notes

### Project Context

This is the **third story in Epic 4** (Financial Management — Premium Tier). This story follows the same inline HTMX CRUD pattern established in Story 2.2 and used in Stories 4.1/4.2, with two unique additions: **live HTMX search** with debounce, and **soft deactivation** instead of hard deletes. The index page uses HTMX for inline create, inline edit, search, filtering, and deactivation.

The Customer model is the first to use **soft deactivation** (`is_active` flag) instead of hard deletes, and the first with a `hasMany` relationship to another feature model (Sales in Story 4.4).

### Soft Deactivation Pattern

The `destroy` action does **NOT** delete the customer from the database. Per the PRD (AC5) and core-workflows.md (Workflow 6), it toggles the `is_active` flag:

```php
public function destroy(Request $request, Customer $customer)
{
    Gate::authorize('delete', $customer);
    $customer->update(['is_active' => false]);

    if ($this->isHtmx($request)) {
        return response('', 200);
    }

    return redirect()->route('app.customers.index')
        ->with('success', 'Customer deactivated.');
}
```

This is safe for the Sale FK relationship: even though `fk_sales_customer` uses `ON DELETE SET NULL`, we never actually delete — so sales retain their customer link. Deactivated customers are simply hidden from the default index view.

[Source: architecture/core-workflows.md#workflow-6, PRD Story 4.3 AC5]

### Search Pattern

The index supports live HTMX search with debounce:

```php
public function index(Request $request)
{
    $query = $request->user()->customers();

    // Status filter (default: active only)
    $status = $request->input('status', 'active');
    if ($status === 'active') {
        $query->active();
    } elseif ($status === 'inactive') {
        $query->where('is_active', false);
    }
    // 'all' — no filter

    // Name search
    if ($request->filled('search')) {
        $query->search($request->search);
    }

    $customers = $query->orderBy('name')->get();

    if ($this->isHtmx($request)) {
        return view('customers.partials.table', compact('customers'));
    }

    return view('customers.index', [
        'customers' => $customers,
        'currentStatus' => $status,
        'search' => $request->search,
    ]);
}
```

The search input uses `hx-trigger="keyup changed delay:300ms"` for a 300ms debounce so we don't fire on every keystroke. Both search and status filter use `hx-target="#customers-body"` to swap the table body partial.

The architecture routing spec (`frontend-architecture.md:153`) defines customers as `Route::resource('customers', CustomerController::class)->except(['show'])`, which implies separate `create` and `edit` pages. This story uses `except(['create', 'edit', 'show'])` with inline HTMX create/edit instead, to align with the PRD epic-level statement: *"These features follow the same HTMX CRUD pattern established in Epic 2."*

The architecture doc should be updated to reflect this decision after the story is accepted.
