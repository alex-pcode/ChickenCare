# Story 5.2: Sales Reports

## Status

Ready for Done

## Story

**As a** premium user,
**I want** to view sales reports with revenue summaries by period,
**so that** I can analyze my sales performance.

## Acceptance Criteria

1. `SalesReportController` with `index` action — premium-only, uses `HandlesHtmx` trait
2. `ReportService` — `getSalesReport(User, ?Carbon $from, ?Carbon $to): array` returning period summary, per-customer breakdown, weekly totals, and monthly totals
3. `sales/reports.blade.php` with date range filter form (HTMX GET) and summary tables
4. Per-customer revenue breakdown: revenue, sale count, and paid/unpaid split per customer
5. Totals by period: weekly and monthly revenue rolled up from filtered sales data

### ReportService Design Rationale

`ReportService` differs from `EggStatsService` and `DashboardService` in that it accepts an optional date range — callers can scope the report to any arbitrary period. The service applies defaults internally, so controllers never need to null-check.

The customer breakdown uses Eloquent collection grouping (not `GROUP BY` SQL) because the dataset is small (per-user, date-filtered) and `with('customer')` eager loading avoids N+1. For users with very large sale volumes, SQL grouping may be preferable — the Dev Agent should document this tradeoff.

The weekly/monthly breakdown reuses the same in-memory collection from `getCustomerBreakdown` — avoid a second DB query by passing the already-loaded collection between private methods, or by loading once and passing down.

### HTMX Date Range Filter Pattern

The filter form uses `hx-get` (not `hx-post`) because date filtering is a read-only, bookmarkable operation:

```blade
<form hx-get="{{ route('app.sales.reports') }}"
      hx-target="#report-content"
      hx-swap="innerHTML"
      hx-push-url="true"
      role="search"
      aria-label="Filter sales by date range">
    <x-forms.date-input name="from" :value="$report['from']->format('Y-m-d')" label="From" />
    <x-forms.date-input name="to" :value="$report['to']->format('Y-m-d')" label="To" />
    <x-forms.submit-button>Apply Filter</x-forms.submit-button>
</form>
```

`hx-push-url="true"` updates the browser URL with the date params, making results bookmarkable and shareable.

### Null Customer Handling

Sales can be recorded without a customer (`customer_id = NULL`). The per-customer breakdown must handle this gracefully. Group null-customer sales under a synthetic entry labelled `'Walk-in / No Customer'` rather than throwing a null reference error.

```php
->groupBy(fn ($sale) => $sale->customer_id ?? 'walk_in')
->map(fn ($sales, $key) => [
    'customer_name' => $key === 'walk_in' ? 'Walk-in / No Customer' : $sales->first()->customer->name,
    'total_revenue'  => $sales->sum('total_amount'),
    'sale_count'     => $sales->count(),
    'paid_amount'    => $sales->where('paid', true)->sum('total_amount'),
    'unpaid_amount'  => $sales->where('paid', false)->sum('total_amount'),
])
```

### Code Quality Assessment

Implementation quality is **good** overall. The single-query-then-group-in-memory design is sound for the expected data volume. Clean controller with a `parseDate()` helper for graceful fallback. Blade templates use proper ARIA attributes, `<caption>` elements on tables, and BEM SCSS. One **sorting bug** was found and fixed (high severity — would produce incorrect customer ordering for revenues >= $1,000).

### Refactoring Performed

- **File**: `app/Services/ReportService.php`
  - **Change**: Added `total_revenue_raw` (float) to customer breakdown entries and changed `sortByDesc` to sort by the raw numeric value instead of the `number_format()`'d string.
  - **Why**: `sortByDesc('total_revenue')` was sorting on formatted strings like "1,000.00". PHP's `<=>` operator casts "1,000.00" to `1.0` (stopping at the comma), causing `$1,000 < $50` in sort order. This is a correctness bug that manifests whenever any customer's revenue reaches $1,000+.
  - **How**: The raw float value is stored alongside the formatted display value. Sort uses the raw value; views continue using the formatted string. The `total_revenue_raw` field can also be useful for future charting or calculations.

- **File**: `tests/Unit/ReportServiceTest.php`
  - **Change**: Added `test_customer_breakdown_sorted_correctly_with_large_values()` with a $1,500 sale to catch the sorting edge case.
  - **Why**: The existing sort test used values of $10 and $50 — too small to trigger the `number_format` comma bug.
  - **How**: Tests both correct ordering and that the formatted value contains the comma ("1,500.00").
