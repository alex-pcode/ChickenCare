### current_count Decrement Logic (AC: 8)

This is the most critical piece of this story. Death records affect `FlockBatch.current_count`:

| Action | Effect on current_count |
|--------|------------------------|
| Create death record | `$batch->decrement('current_count', $death->count)` |
| Update death record | Reverse old count, apply new: `increment(old)` then `decrement(new)` |
| Delete death record | `$batch->increment('current_count', $death->count)` |

**Important considerations:**
- Use Eloquent `increment()`/`decrement()` for atomic DB operations (avoids race conditions)
- `StoreDeathRecordRequest` must validate that `count <= $batch->current_count` to prevent negative bird counts
- On update, validate that the *net change* won't make current_count negative: `current_count + old_count - new_count >= 0`
- The `chk_batch_current` DB constraint (`current_count >= 0`) provides a safety net, but validation should catch this before hitting the DB

### Nested Resource Route Pattern

Both controllers use nested resources under batches. The architecture specifies:
```php
Route::resource('batches.events', BatchEventController::class)
    ->only(['create', 'store', 'edit', 'update', 'destroy']);
Route::resource('batches.deaths', DeathRecordController::class)
    ->only(['create', 'store', 'edit', 'update', 'destroy']);
```

Route model binding gives you both `$batch` and `$event`/`$death` in controller methods. **Always verify the child belongs to the parent:** `$event->batch_id === $batch->id`. Laravel's implicit binding with scoping can handle this if configured:
```php
// In RouteServiceProvider or route definition:
Route::resource('batches.events', ...)->scoped(['event' => 'id']);
```
Or manually check in each controller method.

### user_id on Nested Resources

Both `batch_events` and `death_records` have their own `user_id` column (not just the parent batch's). When creating, explicitly set `user_id`:
```php
$batch->batchEvents()->create([
    ...$request->validated(),
    'user_id' => $request->user()->id,
]);
```
This enables direct ownership queries without joining through batches.

### Coding Standards Reminders

- **Ownership scoping:** Both models have `user_id` — use for ownership checks in policies
- **Nested resource scoping:** Verify child belongs to parent batch in every controller action
- **Validation in Form Requests only** — death count validation against `current_count` goes in the form request
- **Atomic count operations:** Use `increment()`/`decrement()` not `update(['current_count' => ...])` — prevents race conditions
- **HTMX dual responses** on all mutating actions
- **Models are thin** — no business logic in models, count manipulation stays in controllers

### Accessibility Requirements

- Event/death rows: `aria-label` on edit/delete buttons including item description
- Inline forms: `aria-invalid` + `aria-describedby` on error fields
- Delete confirmations: `hx-confirm` provides native browser dialog (accessible)
- Type/cause badges: include text content (not color-only) for screen readers
- Tab content updates: HTMX swaps maintain focus context; ensure form areas have `aria-live="polite"` for screen reader announcement of form loading

### Improvements Checklist

- [ ] **Death record store/update/destroy need DB::transaction wrapping** — `DeathRecordController` performs two related DB operations per action (record CRUD + count adjustment) without a transaction. If the record creation succeeds but `decrement()` fails (or vice versa), `current_count` becomes inconsistent with actual death records. The story notes explicitly call out atomic operations. **Fix:** Wrap each mutating action in `DB::transaction(function() { ... })`:
  ```php
  // store example:
  DB::transaction(function () use ($batch, $request) {
      $batch->deathRecords()->create([...$request->validated(), 'user_id' => $request->user()->id]);
      $batch->decrement('current_count', $request->validated()['count']);
  });
  ```
  Same pattern for `update` (increment old + decrement new + update record) and `destroy` (increment + delete).
- [ ] **DeathRecordSeeder doesn't decrement batch `current_count`** — The seeder creates 2-5 death records per batch but never subtracts their counts from `FlockBatch.current_count`. After seeding, `current_count` is higher than it should be (deaths not reflected). **Fix:** After the inner loop, decrement the batch: `$batch->decrement('current_count', $totalDeaths);`
- [ ] **(Low) Use `response()` helper** — `BatchEventController::destroy` (line 73) and `DeathRecordController::destroy` (line 82) both use `new \Illuminate\Http\Response('', 200)` instead of the `response('', 200)` helper. Consistency with rest of codebase.
- [ ] **(Low) N+1 in dual-ownership policy checks** — `BatchEventPolicy::update/delete` accesses `$batchEvent->flockBatch->user_id`, triggering a lazy load if the relationship isn't eager-loaded. Same for `DeathRecordPolicy`. Low impact at expected scale, but could be optimized by loading the relationship in the controller before the authorize call.
