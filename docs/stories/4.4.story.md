## Dev Notes

### Project Context

This is **Story 4.4**, the final feature story in Epic 4 (Financial Management). It adds the `Sale` model and full HTMX CRUD. This story is a **critical prerequisite** for:

- **Story 5.1 (Dashboard)** — `DashboardService::getFinancialStats()` and `getRecentActivity()` need `$user->sales()`
- **Story 5.2 (Sales Reports)** — `ReportService` is built entirely on the `Sale` model
- **Story 5.3 (Savings)** — `SavingsService::getIncomeSummary()` needs `$user->sales()`

After this story, the Sale model guard patterns noted in Stories 5.1–5.3 can be removed.

### Pattern Reference: Story 4.3 (Customer CRM)

Story 4.4 follows the same inline HTMX CRUD pattern as Story 4.3. Key similarities:
- `HandlesHtmx` trait, `Gate::authorize()`, `except(['create', 'edit', 'show'])` resource route
- Custom `edit-form` and `show-row` routes
- Partials: `entry-row`, `edit-form`, `table`
- CSRF handled via `hx-headers` in app layout

### Unique Additions vs 4.3

| Aspect | Story 4.4 adds |
|--------|---------------|
| Customer dropdown | `$customers` passed to index + editForm — populated from user's active customers |
| Nullable FK | `customer_id` nullable, `withDefault` on the relationship, walk-in label |
| Payment toggle | Dedicated `togglePayment` action + `PATCH` route — swaps row without reloading page |
| Pagination | `paginate(15)` + HTMX pagination, unlike Customer CRM which used `get()` |
| Decimal validation | `total_amount` requires `decimal:0,2` rule for currency precision |

### Customer Dropdown

The customer dropdown must be scoped to the authenticated user's **active** customers only:

```php
$customers = $request->user()->customers()->where('is_active', true)->orderBy('name')->get();
```

The "Walk-in / No Customer" option is a static `<option value="">` at the top of the dropdown. When `customer_id` is submitted as empty string, it should be normalised to `null` by the Form Request or by treating empty-string-validated nullable fields as null via `nullable` rule.

The `Sale` model uses `->withDefault(['name' => 'Walk-in / No Customer'])` on the `customer()` relationship — this means `$sale->customer->name` is always safe to access even when `customer_id` is null.

### Payment Toggle

The toggle pattern uses a dedicated `PATCH` route to avoid conflating payment status with a full edit:

```blade
<button hx-patch="{{ route('app.sales.toggle-payment', $sale) }}"
        hx-target="#sale-{{ $sale->id }}"
        hx-swap="outerHTML"
        aria-label="{{ $sale->paid ? 'Mark as unpaid' : 'Mark as paid' }}">
    {{ $sale->paid ? 'Paid' : 'Unpaid' }}
</button>
```

The `togglePayment` controller action simply flips the boolean and returns the row partial. No Form Request needed (single boolean flip, no user input to validate).

### Route Ordering — Reports Before Resource

If Story 5.2 has already been implemented, `app.sales.reports` (`GET /app/sales/reports`) must be registered **before** `Route::resource('sales', ...)` to prevent Laravel's route model binding from trying to resolve `reports` as a Sale ID:

```php
Route::get('sales/reports', [SalesReportController::class, 'index'])->name('sales.reports');
Route::resource('sales', SaleController::class)->except(['create', 'edit', 'show']);
// ... custom routes
```

If Story 5.2 has not yet been implemented, this ordering still needs to be kept in mind for when it is.

### SCSS — New vs Extend

If Story 5.2 has already been implemented, `_sales.scss` already exists with `.sales-reports` BEM block. Task 15 should **add** the CRUD-specific classes (`.sales`, `.sales__form`, `.sales__badge--paid`, etc.) to the existing file without overwriting the report classes.

If Story 5.2 has not been implemented, create the file and add both CRUD and a placeholder comment for report styles.

### Code Quality Assessment

Solid implementation that closely follows the Story 4.3 HTMX CRUD pattern. Authorization is consistently applied via `Gate::authorize()`, ownership is enforced via `$request->user()->sales()`, and the dual HTMX/redirect response paths are implemented across all mutating actions. The nullable customer FK with `withDefault` is well-handled. Two issues were refactored in-place; one minor DRY concern is left for dev consideration.

### Refactoring Performed

- **File**: `app/Http/Controllers/SaleController.php`
  - **Change**: Added `$sale->load('customer')` to `togglePayment` before returning the view.
  - **Why**: `store` and `update` both call `$sale->load('customer')` before rendering `entry-row`. `togglePayment` omitted this, causing a lazy load on every payment toggle — an inconsistency and a hidden query.
  - **How**: Explicit eager load eliminates the implicit query and aligns the method with the rest of the controller.

- **File**: `app/Models/Sale.php`
  - **Change**: Replaced `whereBetween('sale_date', [$from, $to])` with conditional `where` clauses guarded by null checks.
  - **Why**: `whereBetween` with a `null` bound produces `WHERE sale_date BETWEEN NULL AND x` which silently excludes all rows in MySQL. Story 5.2's `ReportService` calls this scope and may pass one-sided ranges (e.g., from-only or to-only).
  - **How**: Separate `>=`/`<=` clauses are applied only when the bound is non-null, making the scope safe for partial ranges.
