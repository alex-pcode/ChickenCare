# Story 7.1: Static Asset Browser Caching

## Status

Ready for Review

## Story

**As a** returning ChickenCare user,
**I want** static assets to use browser cache policies that match how the app ships files,
**so that** repeat visits are faster without serving stale public assets after deploys.

## Acceptance Criteria

1. Requests for hashed Vite assets under `/build/assets/*` return `Cache-Control: public, max-age=31536000, immutable`.
2. Unhashed media under `/images/*`, `/screenshots/*`, and duplicate `/fonts/*` return `Cache-Control: public, max-age=3600, must-revalidate`.
3. Root unhashed files such as `/favicon.ico` and `/robots.txt` return `Cache-Control: public, max-age=300, must-revalidate`.
4. No rule applies `immutable` or one-year caching to an unhashed path.
5. Static-file header ownership remains in Apache via `public/.htaccess`, not Laravel middleware.
6. Deployment notes explain why immutable caching is safe only for fingerprinted files and call out duplicate `public/fonts/` as a cleanup or validation follow-up.
7. Validation uses a built environment that serves real `/build/assets/*` files rather than only checking `pnpm run dev` responses from `:5173`.

## Dev Notes

### Source Findings

- `vite.config.js` only defines `resources/scss/app.scss` and `resources/js/app.js` as build inputs.
- `package.json` uses `vite build` for `build` and `vite` for `dev`.
- `public/build/manifest.json` confirms hashed filenames for the main JS, CSS, and SCSS-imported Fraunces fonts under `/build/assets/*`.
- `resources/views/layouts/app.blade.php` and `resources/views/layouts/guest.blade.php` load the bundle through `@vite`, which means the app already consumes the fingerprinted output path.
- The repo also serves many unhashed public files directly from `public/`, including `images`, `screenshots`, `favicon.ico`, `robots.txt`, and duplicate font files under `public/fonts`.
- `DEPLOY.md` documents production as Apache on Plesk with manual uploads of `public/build/`, so in-place replacement of unhashed files is a real invalidation risk.
- `public/.htaccess` already exists for rewrite handling but does not currently define cache policy.

### Implementation Notes

- Static asset headers should stay at the web-server layer; Laravel middleware should not own file responses from `public/`.
- Matching order matters. A broad extension-based rule would make it too easy to accidentally label unhashed public media as immutable.
- `public/fonts` should be treated as a temporary safety-net surface, not as equivalent to Vite-emitted hashed fonts.
- Validation for `/build/assets/*` must run against a built environment, because `composer dev` serves frontend assets from the Vite dev server on `:5173`.

### Code Quality Assessment

The `.htaccess` change is small, focused, and well-designed. The implementation correctly leans on Apache (the production web server) rather than Laravel middleware for static-file responses, which avoids booting PHP for assets and matches the guidance in `docs/architecture/security-and-performance.md`. The `RewriteRule [E=...]` + `Header always set ... env=...` pattern is the right idiom for path-conditional headers in Apache and keeps each cache policy mutually exclusive by URL prefix. `DEPLOY.md` clearly captures the *why* of immutable caching and flags the duplicate `public/fonts/` path as a follow-up.

The hashed-asset regex `^/build/assets/.+-[A-Za-z0-9_-]{8,}\.[A-Za-z0-9]+$` was cross-checked against the current build manifest:

- `assets/app-BL0cYPyJ.js` → matches
- `assets/app-DxvgWbFR.css` → matches
- `assets/fraunces-400-MH2cmx7r.woff2` → matches (`.+` consumes `fraunces-400`, hash `-MH2cmx7r` satisfies the 8+ char tail)

Non-hashed files such as `public/build/manifest.json` correctly fall through to Apache defaults (no `immutable` rule applied), satisfying AC4.

### Security Review

No security concerns. The policy only widens cacheability for explicitly enumerated public paths; nothing under `/app/*`, auth, or API endpoints is affected, and dynamic responses remain governed by `CacheHeadersTest` (private, no-store). The `manifest.webmanifest` exemption added beyond ACs is reasonable (it is publicly served and benign).

### Performance Considerations

Net positive once verified. Immutable hashed assets eliminate revalidation round-trips for repeat visitors, and the conservative one-hour / five-minute policies on unhashed files prevent stale-after-deploy regressions on Plesk's manual upload flow. No measured before/after metrics were captured; consider a follow-up Lighthouse run after AC7 verification.
