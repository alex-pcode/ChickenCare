# Story 5.3: Savings & Viability Calculators

## Status

Ready for Done

## Story

**As a** premium user,
**I want** to see financial analysis and viability calculations,
**so that** I can understand my farm's profitability.

## Acceptance Criteria

1. `SavingsController` with `index` action — premium-only, read-only financial analysis page
2. `SavingsService` — `getFinancialAnalysis(User): array` returning income vs expenses, profit margins, and cost per egg
3. `ViabilityController` with `index` action (form display) — premium-only; accepts optional query params for calculation inputs
4. `ViabilityService` — `calculate(User, array $inputs): array` returning cost/profit per bird, monthly projections, and break-even analysis
5. `savings/index.blade.php` and `viability/index.blade.php` with appropriate views
6. Feature SCSS: `resources/scss/features/_savings.scss` and `resources/scss/features/_viability.scss`, both imported in `app.scss`

## Dev Notes

### Project Context

This is **Story 5.3**, the last feature-building story in Epic 5. It delivers two distinct features:

1. **Savings Analysis** (`/app/savings`) — a retrospective financial summary using existing recorded data (expenses + sales). Read-only, no user inputs.
2. **Viability Calculator** (`/app/viability`) — a prospective "what-if" calculator where the user inputs assumptions (bird count, laying rate, pricing, costs) to project profitability. Parameterised form with HTMX result updates.

Both pages are premium-only. Both are blocked by the existing `['premium']` middleware group.

### Critical Dependency: Sale Model (Story 4.4)

`SavingsService::getIncomeSummary()` uses `$user->sales()`. The `Sale` model does not exist yet. The expense analysis (`getExpenseSummary`, `getPerEggMetrics`) works without it — `Expense` and `EggEntry` models exist.

**Interim approach:** Implement `SavingsService` with a guard:
```php
private function getIncomeSummary(User $user): array
{
    if (!class_exists(\App\Models\Sale::class)) {
        return ['total_revenue' => 0, 'paid_revenue' => 0, 'unpaid_revenue' => 0, 'this_month_revenue' => 0, 'sale_count' => 0];
    }
    // ... normal implementation
}
```
Remove the guard once Story 4.4 is complete.

`ViabilityService` has **no dependency on Sale model** — it only reads flock batches and expenses, both of which exist.

### ViabilityService — Pure Calculation

`ViabilityService::calculate()` is a pure function: no DB writes, no side effects. Its inputs are user-supplied parameters (not validated via Form Request — these are calculator inputs, not persisted data). Input normalisation happens inside the service:

```php
$birds = max(1, (int) ($inputs['birds'] ?? $defaults['birds']));
$layingRate = min(1.0, max(0.0, (float) ($inputs['laying_rate'] ?? 0.7)));
```

The service echoes normalised inputs back in `results['inputs']` so the view can repopulate the form correctly after an HTMX update.

### Viability Calculator — HTMX GET Pattern

The calculator uses `hx-get` (not `hx-post`) since it performs no mutations:

```blade
<form hx-get="{{ route('app.viability.index') }}"
      hx-target="#viability-results"
      hx-swap="innerHTML"
      hx-push-url="true"
      hx-indicator="#calc-loading">
```

`hx-push-url="true"` ensures the URL reflects the current inputs — users can bookmark or share their specific calculation setup.

### ViabilityController — Single Route, Two States

The viability route has two states on the same URL:

| State | Trigger | Controller behaviour | View |
|-------|---------|---------------------|------|
| Initial load | No calculator params in URL | `$results = null` | Full page with placeholder |
| After calculation | `?birds=N&...` params present | `$results = $viabilityService->calculate(...)` | Full page with results embedded |
| HTMX recalculate | HTMX GET with params | `$results` computed | Partial only |

Presence check: `$request->hasAny(['birds', 'laying_rate', 'price_per_dozen'])` — if any calculator key is present, run the calculation.

### Savings — Expense Categories

`Expense::category` is a string column (values: `feed`, `medical`, `equipment`, `housing`, `utilities`, `other` per `data-models.md`). The `by_category` breakdown uses `DB::raw()` with `groupBy`:

```php
$user->expenses()
    ->select('category', DB::raw('SUM(amount) as total'))
    ->groupBy('category')
    ->pluck('total', 'category')
```

Display category labels in Title Case in the view (e.g., `ucfirst($category)`).

### Break-Even Calculation Edge Cases

| Scenario | Result |
|----------|--------|
| `monthly_profit > 0` and `cost_per_bird > 0` | `break_even_months = ceil(acquisition_cost / monthly_profit)` |
| `monthly_profit <= 0` | `break_even_months = null` (never breaks even) |
| `cost_per_bird = 0` | `break_even_months = null` (no acquisition cost to recoup) |
| `annual_roi_pct` only shown if `acquisition_cost > 0` | Prevents division-by-zero |

The view must handle `null` for both `break_even_months` and `annual_roi_pct` gracefully — show "N/A" or hide the section.

Route::get('savings', [SavingsController::class, 'index'])->name('savings.index');
Route::get('viability', [ViabilityController::class, 'index'])->name('viability.index');

### Accessibility Requirements

- **Savings page:** Section headings use `<h2>` or `<x-layout.section>` — each major section (Income, Expenses, Profitability, Per-Egg) labelled semantically
- **Metric cards:** positive values: `aria-label="Net profit: $X.XX"`, negative: indicate loss explicitly
- **Viability form:** All inputs have `<label>`, `for`/`id` pair; numeric inputs have `min`, `max`, `step` attributes
- **Calculator results:** `role="region"` + `aria-label="Viability calculation results"` on `#viability-results`
- **Not-viable notice:** `role="alert"` so screen readers announce it when injected via HTMX
- **Empty states:** `role="status"` via `<x-ui.empty-state>`

## QA Results

### Review Date: 2026-04-15

### Reviewed By: Quinn (Test Architect)

### Code Quality Assessment

Implementation quality is **very good** across both features. `SavingsService` provides a clean financial analysis with raw numeric returns (avoiding the `number_format` sorting pitfall found in Story 5.2). `ViabilityService` is a well-implemented pure calculation service with proper input normalization, bounds clamping, and edge-case handling for division by zero and null break-even scenarios. Both controllers follow the project's patterns. Blade views properly handle null/empty states and use semantic HTML with ARIA attributes.

### Refactoring Performed

- **File**: `app/Services/ViabilityService.php`
  - **Change**: Added optional `?array $defaults = null` parameter to `calculate()`. When provided, skips the internal `getDefaults()` DB call.
  - **Why**: The controller calls `getDefaults()` to populate the form, then `calculate()` also called `getDefaults()` internally — resulting in duplicate DB queries (2 queries for flock count + 1 for feed expenses, doubled = 6 total). On HTMX recalculation requests, the controller's `$defaults` was fetched but not used by the partial view.
  - **How**: Controller now passes its already-fetched `$defaults` to `calculate()`, eliminating the redundant DB call. Existing callers that omit the parameter get the same behavior as before (defaults fetched internally).

- **File**: `app/Http/Controllers/ViabilityController.php`
  - **Change**: Passed `$defaults` as third argument to `$viabilityService->calculate()`.
  - **Why**: Completes the optimization — ensures the controller's pre-fetched defaults are reused.
  - **How**: Zero behavior change, just removes ~3 unnecessary DB queries per calculation request.
