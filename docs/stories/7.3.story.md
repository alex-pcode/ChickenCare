# Story 7.3: HTMX History Cache Review and Tuning Decision

## Status

Done

## Story

**As a** ChickenCare user navigating with HTMX boost,
**I want** back and forward navigation to feel fast without restoring misleading stale views,
**so that** history behavior is only tuned when actual browser behavior justifies it.

## Acceptance Criteria

1. The current baseline is documented: `resources/js/app.js` exposes HTMX but does not set explicit `historyCacheSize`, `refreshOnHistoryMiss`, or `getCacheBusterParam` overrides.
2. Browser review covers dashboard, expenses, account tab changes, CRM tab changes, at least one premium route, and one mutation followed by back navigation.
3. The review records for each scenario whether HTMX restored from history, issued a network request, showed a skeleton, and interacted with route warmup logic.
4. The final decision is one of exactly three paths: keep implicit defaults, codify current defaults, or increase `historyCacheSize`, with the reason and rollback note documented.
5. Any config change is gated on observed browser behavior after Stories 7.1 and 7.2 are complete.
6. The review explicitly records stale-content tolerance after create, update, or delete flows before recommending a larger history cache.

## Dev Notes

### Source Findings

- `resources/js/app.js` imports HTMX and exposes `window.htmx`, but there are no explicit `htmx.config` overrides for history behavior.
- `resources/views/layouts/app.blade.php` enables `hx-boost` on the body and includes first-paint skeleton markup and warm-route metadata.
- The route warmup flow in `resources/js/app.js` sends `HX-Request`, `HX-Boosted`, and `X-Requested-With` headers and schedules work with `requestIdleCallback` when available.
- The server also includes a warm-route command in `app/Console/Commands/WarmupRoutes.php` and `routes/console.php`.
- Repository notes already establish that HTMX lifecycle listeners must stay bound to `document` because boosted swaps replace the body element.
- Discovery review already found that at least one authenticated forward navigation restored without a fresh network request, so this story is validating a real current behavior rather than speculating about future optimization.

### Implementation Notes

- Story 7.3 should run after Stories 7.1 and 7.2 so HTTP-cache behavior is no longer ambiguous during browser review.
- If the review shows current defaults are acceptable, documenting that decision is a valid completion path.
- If a config change is justified, the first change should be small and reversible and should be recorded in the story with the exact reason and rollback note.
- History restore behavior should be evaluated separately from first-load skeleton behavior; skipping a skeleton on history restore may be desirable rather than a bug.

## Testing

- Primary validation is browser-based and requires an authenticated session.
- Cover dashboard, expenses, account tabs, CRM tabs, one premium route, and one mutation-then-back scenario.
- For each run, note whether the page restored from HTMX history, whether a network request occurred, and whether the skeleton path was skipped.

### Local testing setup

- Run scenarios against `http://127.0.0.1:8000/app` via `php artisan serve`.
- **Vite dev server must not be running.** Build the bundle once with `pnpm run build`, then start `php artisan serve` on its own. Do not use `composer dev` or `pnpm run dev` for this story — HMR injects extra `:5173` requests and module reloads that distort the "did HTMX restore from history?" signal.
- Quick sanity check: in DevTools → Network, reload `/app/dashboard`. If you see requests to `localhost:5173/@vite/client` or `*.js?t=<timestamp>`, Vite is still in the picture — stop it and rebuild.
- Production-only verification is **not** required for this story. Story 7.2's middleware behaves identically locally and in prod, and Story 7.1's Apache header emission is orthogonal to HTMX history-cache behavior.

**Key Findings:**

1. **Cross-page back navigation ALWAYS makes fresh requests**: All back navigations between different routes triggered new network requests due to `Cache-Control: private, no-store` headers from `SetDynamicResponseCacheHeaders` middleware (Story 7.2).

2. **Same-page tab navigation uses HTMX history cache**: Back navigation from `?tab=security` to `/app/account` and from `?tab=customers` to `/app/crm` did NOT trigger network requests. HTMX restored from history cache.

3. **Mutation state is always fresh**: After creating an egg entry, navigating away and back triggered a fresh request, ensuring the state reflects the mutation.

4. **Route warmup is irrelevant for history navigation**: The `no-store` headers prevent browser caching, so pre-warmed routes don't help with back navigation. Warmup only helps with forward navigation (first visit).

5. **Skeleton loading is active on fresh requests**: All fresh requests returned full HTML with skeleton styles, confirming the skeleton listener path works as designed.

**Decision (AC: 4, 5):**

**Keep HTMX history configuration implicit.**

**Reason:**
- The `SetDynamicResponseCacheHeaders` middleware (Story 7.2) intentionally sets `Cache-Control: private, no-store` on all dynamic responses.
- This ensures users always see fresh data, which is critical for a data-entry application where mutations are frequent.
- HTMX's history caching only works for same-page query parameter changes (tabs), which is appropriate behavior.
- Cross-page history restore is correctly blocked by server headers, not client config.

**No config change needed.** Increasing `historyCacheSize` would have no effect because the server's `no-store` directive prevents browser caching regardless of cache size.

**Stale-content tolerance (AC: 6):**
- After mutation (create egg entry), back navigation made fresh request and returned updated state.
- No stale content risk observed with current setup.

**Rollback note:** Not applicable (no config changes made).
